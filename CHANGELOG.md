## Unreleased

Why: the settings of a person and of an instance move from files into the database (ADR 0100, ADR 0086 addendum; PLAN `speicher-schnittstelle`). This is part A of that round: the typed tables and the row functions in this crate; the program `fs-settings` (parts B and C) builds on them. Written by Claude (Anthropic) as a probe; waits for review.

- `v5::setting` (feature `v5`): the table family `settings_*`, schema version 5 (five steps): `settings_rev`, `settings_profile` (base = id 0; a deleted profile stays as a tombstone, its name is free again, its id is never issued again), `settings_active` (the active profile of this device), `settings_value` (typed: `kind` bool/int/text with `v_int`/`v_text` and a `CHECK` per kind, no JSON, no blob), `settings_instance_value`, `settings_instance_lock` (a lock never exists without its value; reason mandatory), `settings_instance_log` (append-only by triggers).
- `v5::setting::SettingRows`: `open`, `new`, `rev`, `values`, `put`, `clear_profile`, `index`, `change_index` (read-change-write in ONE transaction; an error of the closure changes nothing), `instance`, `put_instance` (idempotent: `Outcome::Same`), `lock`, `unlock` (reason mandatory, c0 decision 6), `log`. Every write is one transaction with `rev + 1`. Refusals are `Error::Invalid` with `table.column` and a reason code (`unknown`, `id-invalid`, `exists`, `locked`, `reason-missing`).
- `Store::inspect(path, domain) -> Inspect::{Absent, Fits, Newer, Broken}`: looks at a store file WITHOUT changing it (works on a throw-away copy in a folder beside the file that is removed again; the file, its length, its modification time and its folder stay the same).
- New `Error::Newer { domain, found, known }` (additive; `Error` is `non_exhaustive`): a store with more steps than the program knows. Before, this was `Error::Schema` with a sentence.
- `cargo fmt --all` on the v0.0.8 base (import order, line breaks) in a separate commit.

## 0.0.8

Why: the migration scaffold of the untagged v0.0.7 could, by its first review (Opus, conditions 1 to 6), still hurt a person's data in rare cases (it opened the v4 file read-write, it could run while the program wrote to it, it left a half-built file after an error, it let the fall-back give up work silently, it dropped envelope times without saying so). This version closes those holes before any real converter is written; data safety comes first. v0.0.7 was never tagged: its content is listed here too.

- Read-only source (condition 1): `TursoStore::open_read_only(path, options)` opens a file without write access and refuses it unless its schema version is exactly 4 (message `the file has schema version N, expected 4`); it never migrates and never makes an identity. `MigrationPlan::check` first takes the lock, then opens the v4 file read-only, and only then makes the backup. Tested with SHA-256 of every file in the folder before and after for version 0, 3, 4, 5, an empty file, a foreign file and a real v5 file: nothing appears, vanishes or changes.
- The program must be closed (condition 5): `check` holds an exclusive advisory lock (`flock`, `SourceLock`) on the v4 file during backup, check and conversion; when another handle holds one, `check` stops with the hint to close the program. At the end the fingerprint (SHA-256 of the file and its `-wal`) must be the one from before, else the run is aborted. No Windows promise.
- Envelope times and media type (condition 2): an object with `start_time` or `end_time` is HELD BACK with the reason unless its `Converter` says `carries_times()` (then `export_times` is compared by the round trip); an object whose `content_type` is not the one `Converter::content_type` writes is HELD BACK. Nothing is dropped silently.
- Fall-back (condition 3): `fall_back(confirm_loss)`; from `Switched` it is REFUSED when the new file differs from the moment of the switch (fingerprint kept in the state file; unknown counts as changed), unless `confirm_loss` is true; the state file then says `loss=confirmed`. Before the switch nothing can be lost.
- Aborted check (condition 4): a check that fails after it created files removes exactly those (the half-built `.v5` with its `-wal`/`-shm`, the backup of this run, a report) and says so in the error and in `MigrationPlan::abort_note`; files that were there before are never touched, an existing `.v5` still stops the run before anything is made. The run can be repeated from the start. Tested with an error injected in the middle of the run.
- `check::typed` (condition 6): columns of the new logical type `free_text` (`Logical::FreeText`) and the core columns `objects.name`, `activity_change.old_text/new_text` (`check::FREE_TEXT_CORE`) are exempt from the JSON heuristic (a note `[1,2]` or `{}` is no finding); a column of the type `ANY` is a finding (`Rule::AnyType`). The migrated file is checked with standard SQLite (`integrity_check`, no orphan autoindex, `-wal` beside it) in a test.
- The original is carried: the v4 original becomes `object_original` (bytes, media type, SHA-256) and is compared by the round trip. Still held back, with the reason in the report: addressing, protection categories (their tables follow), a `context`/`in_reply_to`/`describes` that is no object id. Counted as skipped: the v4 activity history (carried by a later step) and the derived index fields. No program has a real converter yet: they come with the programs.
- Auf Deutsch: Warum: das Migrationsgeruest des nie getaggten v0.0.7 konnte nach seiner ersten Pruefung (Opus, Auflagen 1 bis 6) in seltenen Faellen noch Daten gefaehrden (v4-Datei les-schreibend geoeffnet, Lauf waehrend das Programm schreibt, halbe Datei nach einem Fehler, Rueckfall gab Arbeit still auf, Hüllzeiten ohne Hinweis verworfen). Diese Version schliesst die Luecken vor dem ersten echten Umwandler; Datensicherheit zuerst. v0.0.7 wurde nie getaggt, sein Inhalt steht hier mit.
- Quelle nur lesend (Auflage 1): `TursoStore::open_read_only` oeffnet ohne Schreibrecht und lehnt jede Datei ausser Schema-Version 4 ab; `check` sperrt zuerst, oeffnet dann lesend und sichert danach. Test mit SHA-256 aller Dateien vorher/nachher bei Version 0, 3, 4, 5, leerer, fremder und echter v5-Datei.
- Programm muss geschlossen sein (Auflage 5): exklusive Sperre (`flock`) auf der v4-Datei waehrend Sicherung, Pruefung und Umwandlung; haelt sie ein anderer Griff, bricht `check` mit Hinweis ab; am Ende muss der Fingerabdruck (SHA-256 von Datei und `-wal`) unveraendert sein. Keine Windows-Zusage.
- Hüllzeiten und Medientyp (Auflage 2): `start_time`/`end_time` und abweichender `content_type` fuehren zu ZURUECKGEHALTEN mit Grund, ausser der `Converter` traegt sie (dann vergleicht der Rundlauf); nichts wird still verworfen.
- Rueckfall (Auflage 3): `fall_back(confirm_loss)`: aus `Switched` abgelehnt, wenn die neue Datei sich seit der Umschaltung geaendert hat (Fingerabdruck im Zustandsfile; unbekannt gilt als geaendert), ausser `confirm_loss` ist true; der Zustand vermerkt `loss=confirmed`.
- Abgebrochene Pruefung (Auflage 4): ein Fehler raeumt genau die in diesem Lauf erzeugten Dateien weg (halbe `.v5` samt Nebendateien, Sicherung, Bericht) und meldet das im Fehler und in `abort_note`; Vorhandenes wird nie angefasst; der Lauf kann neu beginnen. Test mit eingespritztem Fehler mitten im Lauf.
- `check::typed` (Auflage 6): Freitext-Spalten (`Logical::FreeText`, Kernspalten `FREE_TEXT_CORE`) sind von der JSON-Heuristik ausgenommen (Notiz `[1,2]` oder `{}` ist kein Befund); Spalten vom Typ `ANY` sind ein Befund (`Rule::AnyType`); die migrierte Datei wird mit Standard-SQLite geprueft (Test).
- Das Original wird uebernommen (`object_original`, Rundlauf-Vergleich). Weiter zurueckgehalten mit Grund im Bericht: Adressierung, Schutzkategorien (Tabellen folgen), `context` ohne Objekt-Id; als uebersprungen gezaehlt: v4-Aktivitaetshistorie und abgeleitete Suchfelder. Noch kein Programm hat einen echten Umwandler: er kommt mit dem Programm.

Contents of the untagged v0.0.7 (scaffold):

- Migration scaffold v4 to v5 (feature `v5`, module `v5::migrate_v4`): backup `<file>.v4.bak` (never overwrites, a taken name is numbered, the copy is verified by SHA-256, a `-wal` file is copied too), a NEW file `<file>.v5`, one `Converter` per program (v4 JSON content to typed rows, the way back from the rows, a documented `normalize`), a round trip per object (envelope and content read back from the new file and compared; v4 microseconds are rounded to milliseconds and counted), a written report `<file>.migration-report.txt` (converted, held back with reason, skipped, rounded, duration, backup). What does not round-trip or is not carried yet (addressing, protection categories, original, non-id `context`) is HELD BACK and stays in the v4 file; the v4 activity history is not carried yet and reported as skipped. `MigrationPlan` is the switch: Checking, Ready, Confirmed, Switched, `FellBack`; the v4 file stays the active one until a person confirms (`confirm`, then `switch`); the state is kept in `<file>.migration-state`. Data is never converted automatically. Example converter for the test domain `notes`.
- `v5::check::typed`: checks a real v5 file (catalogue and data): every table `STRICT`, no JSON in a text column (heuristic), no `value_kind object` value that is not an object id, time columns `INTEGER`, a foreign key on every `REF` column (except `*_abzug`, the core columns in `REF_WITHOUT_FK`; a person IRI needs none), no blob except `object_original.bytes`, a column `cipher` (the nonce is part of it) and `collab_buffer.loro`, every table registered. Returns all findings. No CLI exists in this crate, so there is no command line call.
- `value_kind object` is checked: in the v5 code it is a TEXT column that holds an object id of the own store (`LogValue::Object`), not JSON; the undo of an inserted or deleted child row must be a typed copy of the row (shadow table), never an `object` blob (decision 2026-11-17).
- Auf Deutsch: Migrationsgeruest v4 nach v5 (Feature `v5`, Modul `v5::migrate_v4`): Sicherung `<Datei>.v4.bak` (ueberschreibt nie, belegter Name wird nummeriert, Kopie per SHA-256 geprueft), NEUE Datei `<Datei>.v5`, ein `Converter` je Programm, Rundlauf je Objekt (Huelle und Inhalt aus der neuen Datei zurueckgelesen und verglichen; v4-Mikrosekunden werden auf Millisekunden gerundet und gezaehlt), Bericht `<Datei>.migration-report.txt` (umgewandelt, zurueckgehalten mit Grund, uebersprungen, gerundet, Dauer, Sicherung). Was nicht rundlaeuft oder noch nicht uebernommen wird (Adressierung, Schutzkategorien, Original, `context` ohne Objekt-Id), wird ZURUECKGEHALTEN und bleibt in der v4-Datei; die v4-Aktivitaetshistorie folgt spaeter und steht im Bericht als uebersprungen. `MigrationPlan` ist der Umschalter: Pruefen, Bereit, Bestaetigt, Umgeschaltet, Rueckfall; bis ein Mensch bestaetigt, bleibt die v4-Datei die aktive. Daten werden nie automatisch umgewandelt. Beispiel-Umwandler fuer die Testdomaene `notes`.
- `v5::check::typed` prueft eine echte v5-Datei (alle Tabellen `STRICT`, kein JSON in Textspalten, kein `object`-Wert der keine Objekt-Id ist, Zeitspalten `INTEGER`, Fremdschluessel an `REF`-Spalten ausser Personen-Abzug und den Kernspalten, Blobs nur Original, `cipher` samt Nonce und `collab_buffer.loro`, alle Tabellen registriert) und liefert alle Befunde. `value_kind object` ist im v5-Code eine Objekt-Id (TEXT), kein JSON; Undo einer Kindzeile wird eine typisierte Zeilenkopie, nie ein `object`-Blob.

## 0.0.5

- The typed log (v5) knows the five AS2 activity kinds `Add`, `Remove`, `Join`, `Leave` and `Move` (`v5::log::Kind`, 13 kinds now), which fs-tasks needs. Per ADR 0086 (addendum 2026-11-16) the kinds are a word table `fs_word` (`kind`, `code`, `builtin`, ...), not a `CHECK` list: new steps 4 to 7 of the store's own domain create it, insert the eight old kinds and the five new ones as built-in words (`ON CONFLICT (kind, code) DO UPDATE SET builtin = 1`), and rebuild `activity` (staging tables, no `ALTER TABLE ... RENAME`) so that `(kind_set, kind)` is a foreign key into it; old rows are copied unchanged. Steps 1 to 3 and their fingerprints are unchanged (a test pins them). New column `activity.kind_set` (always `activity_kind`). The word table is the single table `fs_word` (ADR 0086 open point 6), because turso 0.8.3 renames the autoindex of any table whose name starts with `activity_` when `activity` is renamed, which standard SQLite then refuses. No pin or dependency changes.
- Auf Deutsch: Das typisierte Protokoll (v5) kennt zusaetzlich die fuenf AS2-Aktivitaetsarten `Add`, `Remove`, `Join`, `Leave`, `Move` (jetzt 13 Arten). Nach ADR 0086 (Nachtrag 16.11.) stehen die Arten in einer Wort-Tabelle `fs_word` statt in einer `CHECK`-Liste: neue Schritte 4 bis 7 der eigenen Domain legen sie an, tragen die acht alten und die fuenf neuen Arten als eingebaute Woerter ein und bauen `activity` so um, dass `(kind_set, kind)` per Fremdschluessel darauf zeigt; alte Zeilen bleiben erhalten. Schritte 1 bis 3 und ihre Fingerabdruecke bleiben unveraendert. Pins und Abhaengigkeiten unveraendert.
