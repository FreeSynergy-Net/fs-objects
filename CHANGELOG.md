NOTE / HINWEIS: The migrator (`v5::migrate_v4`) stays unchanged and UNUSED. The lock gap (A1/A2) is closed in this release, but by the user's rule (W3, 2026-11-18) there is no data migration or rescue until the first real users exist, and no program has a real converter; so do not use it until then. / Der Umwandler (`v5::migrate_v4`) bleibt unveraendert und UNGENUTZT. Die Sperr-Luecke (A1/A2) ist in dieser Version geschlossen, aber nach der Nutzerregel (W3, 18.11.2026) gibt es keine Datenmigration und keine Rettung, bis es erste echte Nutzer gibt, und kein Programm hat einen echten Umwandler; bis dahin nicht benutzen.

- A1 (review umwandler-3, Opus 2026-11-18): the lock of the migrator held only until the first read. A POSIX `fcntl` lock belongs to the PROCESS and ends when ANY descriptor of the file is closed, and `fingerprint` and the backup opened and closed the v4 file, so a program that started DURING the check was not kept out. The store files (v4 and v5) are now read through one descriptor per file that is never closed (`pread`, new module `keep`), and `SourceLock` unlocks explicitly instead of closing. Tested with a real `TursoStore` in a child process that starts AFTER the lock and the read (also during a running `check`): it is refused. Limit stays: a program in the SAME process is not seen by the lock (the program must be closed before `check`).
- A2: `confirm`, `switch` and `fall_back` read the v4 or v5 file, which may be open in the program's own process; the close of that read silently removed the program's engine lock, so a second instance could open the same file for writing (damage risk). They now read through the never-closed descriptor and leave the program's lock alone. Tested for `fingerprint`, `confirm`, `switch` and `fall_back` with a program open in the test's process and a child process that tries to open the file.
- K1: a test for an original with the same bytes under another media type (the comparison of the media type in the round trip had no test that failed without it).
- K2 (flow, DESIGN): the program stays closed from `check` until `switch`; when a program opens the v4 file in between, the engine creates a `-wal` file, the fingerprint differs and `confirm`/`switch` refuse (safe, but a new check is needed).

Why: the migration scaffold of the untagged v0.0.7 could, by its first review (Opus, conditions 1 to 6), still hurt a person's data in rare cases (it opened the v4 file read-write, it could run while the program wrote to it, it left a half-built file after an error, it let the fall-back give up work silently, it dropped envelope times without saying so). This version closes those holes before any real converter is written; data safety comes first. v0.0.7 was never tagged: its content is listed here too.

- Read-only source (condition 1): `TursoStore::open_read_only(path, options)` opens a file without write access and refuses it unless its schema version is exactly 4 (message `the file has schema version N, expected 4`); it never migrates and never makes an identity. `MigrationPlan::check` first takes the lock, then opens the v4 file read-only, and only then makes the backup. Tested with SHA-256 of every file in the folder before and after for version 0, 3, 4, 5, an empty file, a foreign file and a real v5 file: nothing appears, vanishes or changes.
- The program must be closed (condition 5): `check` holds advisory locks (`SourceLock`: the POSIX `fcntl` lock that the engine itself takes on a file it opens, and `flock`) on the v4 file during backup, check and conversion; when another process or handle holds one, `check` stops with the hint to close the program. Tested with a REAL program (an open `TursoStore` in a child process). A program in the same process is not seen by the `fcntl` lock. Windows: not checked yet (the CI caller comes after the cascade). At the end the fingerprint (SHA-256 of the file and its `-wal`) must be the one from before, else the run is aborted. No Windows promise.
- Envelope times and media type (condition 2): an object with `start_time` or `end_time` is HELD BACK with the reason unless its `Converter` says `carries_times()` (then `export_times` is compared by the round trip); an object whose `content_type` is not the one `Converter::content_type` writes is HELD BACK. Nothing is dropped silently.

The run can be repeated from the start. Tested with an error injected in the middle of the run.

The migrated file is checked with standard SQLite (`integrity_check`, no orphan autoindex, `-wal` beside it) in a test.

Contents of the untagged v0.0.7 (scaffold):

- Migration scaffold v4 to v5 (feature `v5`, module `v5::migrate_v4`): backup `<file>.v4.bak` (never overwrites, a taken name is numbered, the copy is verified by SHA-256, a `-wal` file is copied too), a NEW file `<file>.v5`, one `Converter` per program (v4 JSON content to typed rows, the way back from the rows, a documented `normalize`), a round trip per object (envelope and content read back from the new file and compared; v4 microseconds are rounded to milliseconds and counted), a written report `<file>.migration-report.txt` (converted, held back with reason, skipped, rounded, duration, backup). Returns all findings. No CLI exists in this crate, so there is no command line call.

## 0.0.5

- The typed log (v5) knows the five AS2 activity kinds `Add`, `Remove`, `Join`, `Leave` and `Move` (`v5::log::Kind`, 13 kinds now), which fs-tasks needs. Per ADR 0086 (addendum 2026-11-16) the kinds are a word table `fs_word` (`kind`, `code`, `builtin`, ...), not a `CHECK` list: new steps 4 to 7 of the store's own domain create it, insert the eight old kinds and the five new ones as built-in words (`ON CONFLICT (kind, code) DO UPDATE SET builtin = 1`), and rebuild `activity` (staging tables, no `ALTER TABLE ... RENAME`) so that `(kind_set, kind)` is a foreign key into it; old rows are copied unchanged. Steps 1 to 3 and their fingerprints are unchanged (a test pins them). New column `activity.kind_set` (always `activity_kind`). The word table is the single table `fs_word` (ADR 0086 open point 6), because turso 0.8.3 renames the autoindex of any table whose name starts with `activity_` when `activity` is renamed, which standard SQLite then refuses. No pin or dependency changes.
