## Unreleased

- Migration scaffold v4 to v5 (feature `v5`, module `v5::migrate_v4`): backup `<file>.v4.bak` (never overwrites, a taken name is numbered, the copy is verified by SHA-256, a `-wal` file is copied too), a NEW file `<file>.v5`, one `Converter` per program (v4 JSON content to typed rows, the way back from the rows, a documented `normalize`), a round trip per object (envelope and content read back from the new file and compared; v4 microseconds are rounded to milliseconds and counted), a written report `<file>.migration-report.txt` (converted, held back with reason, skipped, rounded, duration, backup). What does not round-trip or is not carried yet (addressing, protection categories, original, non-id `context`) is HELD BACK and stays in the v4 file; the v4 activity history is not carried yet and reported as skipped. `MigrationPlan` is the switch: Checking, Ready, Confirmed, Switched, `FellBack`; the v4 file stays the active one until a person confirms (`confirm`, then `switch`); the state is kept in `<file>.migration-state`. Data is never converted automatically. Example converter for the test domain `notes`.
- `v5::check::typed`: checks a real v5 file (catalogue and data): every table `STRICT`, no JSON in a text column (heuristic), no `value_kind object` value that is not an object id, time columns `INTEGER`, a foreign key on every `REF` column (except `*_abzug`, the core columns in `REF_WITHOUT_FK`; a person IRI needs none), no blob except `object_original.bytes`, a column `cipher` (the nonce is part of it) and `collab_buffer.loro`, every table registered. Returns all findings. No CLI exists in this crate, so there is no command line call.
- `value_kind object` is checked: in the v5 code it is a TEXT column that holds an object id of the own store (`LogValue::Object`), not JSON; the undo of an inserted or deleted child row must be a typed copy of the row (shadow table), never an `object` blob (decision 2026-11-17).
- No version change, no tag (the release run sets 0.0.7).
- Auf Deutsch: Migrationsgeruest v4 nach v5 (Feature `v5`, Modul `v5::migrate_v4`): Sicherung `<Datei>.v4.bak` (ueberschreibt nie, belegter Name wird nummeriert, Kopie per SHA-256 geprueft), NEUE Datei `<Datei>.v5`, ein `Converter` je Programm, Rundlauf je Objekt (Huelle und Inhalt aus der neuen Datei zurueckgelesen und verglichen; v4-Mikrosekunden werden auf Millisekunden gerundet und gezaehlt), Bericht `<Datei>.migration-report.txt` (umgewandelt, zurueckgehalten mit Grund, uebersprungen, gerundet, Dauer, Sicherung). Was nicht rundlaeuft oder noch nicht uebernommen wird (Adressierung, Schutzkategorien, Original, `context` ohne Objekt-Id), wird ZURUECKGEHALTEN und bleibt in der v4-Datei; die v4-Aktivitaetshistorie folgt spaeter und steht im Bericht als uebersprungen. `MigrationPlan` ist der Umschalter: Pruefen, Bereit, Bestaetigt, Umgeschaltet, Rueckfall; bis ein Mensch bestaetigt, bleibt die v4-Datei die aktive. Daten werden nie automatisch umgewandelt. Beispiel-Umwandler fuer die Testdomaene `notes`.
- `v5::check::typed` prueft eine echte v5-Datei (alle Tabellen `STRICT`, kein JSON in Textspalten, kein `object`-Wert der keine Objekt-Id ist, Zeitspalten `INTEGER`, Fremdschluessel an `REF`-Spalten ausser Personen-Abzug und den Kernspalten, Blobs nur Original, `cipher` samt Nonce und `collab_buffer.loro`, alle Tabellen registriert) und liefert alle Befunde. `value_kind object` ist im v5-Code eine Objekt-Id (TEXT), kein JSON; Undo einer Kindzeile wird eine typisierte Zeilenkopie, nie ein `object`-Blob.

The lock has exactly one `fs-types` source and no `fs-interfaces` entry any more. The workflow uses `fs-release` v0.0.10, and `.fs-lock-sources.toml` makes the lock check strict. No code, table or API change; steps 1 to 7 and their fingerprints are unchanged.
- Tests: `standard_sqlite_reads_the_store_file` writes under the test target (`CARGO_TARGET_TMPDIR`), not `/tmp` (RAM), and removes its folder also when it fails; a new test runs the standard-SQLite check (`python3 -I`, with the `-wal` file) on a file migrated from the v0.0.4 shape; the `ON CONFLICT` of step 5 (`WORDS_OLD`) is tested like that of step 6.

## 0.0.5

- The typed log (v5) knows the five AS2 activity kinds `Add`, `Remove`, `Join`, `Leave` and `Move` (`v5::log::Kind`, 13 kinds now), which fs-tasks needs. Per ADR 0086 (addendum 2026-11-16) the kinds are a word table `fs_word` (`kind`, `code`, `builtin`, ...), not a `CHECK` list: new steps 4 to 7 of the store's own domain create it, insert the eight old kinds and the five new ones as built-in words (`ON CONFLICT (kind, code) DO UPDATE SET builtin = 1`), and rebuild `activity` (staging tables, no `ALTER TABLE ... RENAME`) so that `(kind_set, kind)` is a foreign key into it; old rows are copied unchanged. Steps 1 to 3 and their fingerprints are unchanged (a test pins them). New column `activity.kind_set` (always `activity_kind`). The word table is the single table `fs_word` (ADR 0086 open point 6), because turso 0.8.3 renames the autoindex of any table whose name starts with `activity_` when `activity` is renamed, which standard SQLite then refuses. No pin or dependency changes.
- Auf Deutsch: Das typisierte Protokoll (v5) kennt zusaetzlich die fuenf AS2-Aktivitaetsarten `Add`, `Remove`, `Join`, `Leave`, `Move` (jetzt 13 Arten). Nach ADR 0086 (Nachtrag 16.11.) stehen die Arten in einer Wort-Tabelle `fs_word` statt in einer `CHECK`-Liste: neue Schritte 4 bis 7 der eigenen Domain legen sie an, tragen die acht alten und die fuenf neuen Arten als eingebaute Woerter ein und bauen `activity` so um, dass `(kind_set, kind)` per Fremdschluessel darauf zeigt; alte Zeilen bleiben erhalten. Schritte 1 bis 3 und ihre Fingerabdruecke bleiben unveraendert. Pins und Abhaengigkeiten unveraendert.
